# REVIEW.md

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `create_employee` | Checks for duplicates with `find_one` instead of using a unique index, leading to race conditions. | Two concurrent requests with the same `emp_code` might both succeed, resulting in duplicate records. | Removed `find_one` check, added a unique index on `emp_code` in MongoDB on startup, and handled `DuplicateKeyError` to raise 409. |
| 2 | `create_employee` | Uses `datetime.now()` for `created_at` instead of an aware UTC datetime, and returns it as a datetime instead of epoch ms. | The response field `created_at` is an ISO string instead of epoch ms (violating the API contract). | Changed to `datetime.now(timezone.utc)` and mapped the response field to epoch ms by multiplying `.timestamp()` by 1000. |
| 3 | `list_employees` | `skip` logic uses `page * page_size` (1-indexed page). | The first page (`page=1`) would skip the first 20 records. | Changed `skip` to `(page - 1) * page_size`. |
| 4 | `list_employees` | `total` calculation ignores the `department` filter. | When filtering by department, `total` still returns the count of all employees in the collection. | Changed `count_documents({})` to `count_documents(q)`. |
| 5 | `list_employees` | Does not sort by `emp_code` ascending. | The returned list order is not guaranteed. | Added `.sort("emp_code", ASCENDING)` to the PyMongo query. |
| 6 | `punch_in` | Does not handle missing employee code properly. | Passing an unknown `emp_code` causes `emp["shift_start"]` to raise a `TypeError` (500). | Added a check `if not emp:` and raised a 404. |
| 7 | `punch_in` | Uses local naive `datetime` via `datetime.fromtimestamp(ms/1000)` and doesn't truncate to seconds (R1). | If the server timezone is not IST, calculations will be off. Microseconds could affect late minute logic. | Changed to aware UTC datetimes: `datetime.fromtimestamp(ms/1000, tz=timezone.utc)`, and stripped microseconds with `.replace(microsecond=0)`. |
| 8 | `punch_in` | Determines attendance date using local date, disregarding overnight shifts (R1). | For an overnight shift, punching in after midnight records the wrong date. | Re-implemented `get_attendance_date` logic according to R1. |
| 9 | `punch_in` | Vulnerable to race conditions for double punch-ins. | Two concurrent requests can create two records for the same employee and date. | Created unique index on `(emp_code, date)` and handled `DuplicateKeyError`. |
| 10 | `compute_late_minutes` | Fails to properly floor the difference, check strictly > 10 min, and handles date incorrectly. | `minutes > 10` evaluates `False` when minutes=10 from a fraction of seconds, and ignores overnight date offsets. | Re-implemented to use strict seconds difference > 600, floor-divided by 60, using proper IST conversions. |
| 11 | `compute_work_hours` | Uses `round()` which performs Banker's rounding instead of half-up rounding (R4). | Hours like 9.125 might round to 9.12 instead of 9.13. | Re-implemented using `decimal.Decimal` and `ROUND_HALF_UP`. |
| 12 | `compute_overtime` | Incorrectly constructs the `shift_end` datetime, especially for overnight shifts. | Calculates negative or wildly incorrect overtime if the shift crosses midnight. | Re-implemented to correctly identify the calendar date of `shift_end`. |
| 13 | `list_attendance` | Python-side in-memory sort `docs.sort(key=...)` and slice, which is slow for 100k records. | Loading 100k records into memory and sorting causes high memory use and slow response. | Replaced with MongoDB query modifiers: `.sort([("date", DESCENDING), ("emp_code", ASCENDING)]).skip(...).limit(...)`. |
| 14 | `list_attendance` | Incorrectly builds the MongoDB date range query. | If both `date_from` and `date_to` are provided, the query dictionary assignment overrides properties incorrectly or throws an error. | Built the date query progressively: `if date_from: q["date"]["$gte"] = date_from`, etc. |

Also I decided that the initial naive `datetime` use without `tz_aware=True` in PyMongo was a defect, so I enabled `tz_aware=True` to ensure we always work with UTC-aware datetimes.
